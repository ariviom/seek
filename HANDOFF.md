**Renamed to Seek (2026-10-10, ticket 13).** The package, CLI, paths, database file, keychain service, systemd units,
MCP server and tool names (`mcp__seek__…`), `SEEK_*` environment variables and web UI are all Seek now, with the
logo from `docs/brand/`. Entries below this one are history and keep the old name. The old schema's own names
(`mentors`, `mentor_groups`, `mentor_id`…) and `~/.local/share/mentor-baselines` deliberately stay. Drew's
installation moved on 2026-10-10 (all seven steps run, data counts identical before and after, and `seek` MCP
re-registered in both `~/.claude.json` and `~/.claude/.claude.json`). The steps, for the record:

1. `systemctl --user disable --now mentor.service`, then remove `~/.config/systemd/user/mentor.service` and
   `systemctl --user daemon-reload` (no Sync timer is installed).
2. `mv ~/.config/mentor ~/.config/seek`, `mv ~/.local/share/mentor ~/.local/share/seek`, then
   `mv ~/.local/share/seek/mentor.db ~/.local/share/seek/seek.db` (move its `-wal`/`-shm` files too, if present).
   `config.toml` needs no edits: its only mention is the `remote.example.com` hostname, which stays.
3. `uv tool uninstall mentor`, then `uv tool install ~/mentor` from the updated `main` checkout.
4. `seek install-service`. It finds `claude` on PATH by itself, but it records the shell's `CLAUDE_CONFIG_DIR`, so
   first check that `echo $CLAUDE_CONFIG_DIR` prints `/home/drew/.claude`, the login the current unit uses, and
   not a work profile.
5. Keys: nothing to move. This installation has no `secrets.json` and no keychain item. Were there a journal, it
   would have to be deleted before entering a key: otherwise replacing the key tries to delete the old item under
   the service `seek`, fails because it lives under `mentor`, and falls back to storing the new key in the file.
6. Re-register MCP clients: `claude mcp remove mentor --scope user`, then the `claude mcp add …` line from
   `seek mcp-config`.
7. Check: `seek status`, then confirm in the web UI that Channels, Conversations and search are all intact. Each
   Conversation's first CLI turn after the move starts a fresh Claude session and replays the stored history,
   because Claude Code keys its sessions by the moved `chat/` path. That is expected, not data loss.

## Codebase conventions so far
- `create_app(config, transcripts, embedder, reranker, cli_engine, static_dir, sync_poll_seconds, events_keepalive_seconds, model_progress_seconds, sql_time_limit_seconds, fetch_access_keys, access_keys_refetch_seconds, secrets, api_engine, check_seconds, clock)`: each port is its own argument, added when its first consumer lands; `secrets` and `api_engine` default to the production `KeyringSecrets` and an `ApiEngine` over it. Lifespan loads the models in the background and starts the `SyncWorker` task (`sync_worker.py`), which is woken on enqueue and on model state changes, and polls; it runs Syncs only while holding the `sync_lease` row, and only once the embedding model is ready (or has failed). `seek serve` wires `YouTubeTranscriptSource` (yt-dlp, `youtube.py`, settings from `youtube_*` config), the real models from `models.py` sharing one `GpuRunner`, and `ClaudeChatEngine` with `claude_cli_path` or else the `claude` on PATH. `channels_router` and `playlists_router` take `config.min_duration_seconds`, because their deletes run the keep rule (see Library below).
- Service: `seek install-service` (`cli.install`) calls `service.install_service(config, env, seek_executable, unit_dir, systemctl)`, which writes `seek.service` (the shell's PATH, `SEEK_*` and a few location variables, the Claude CLI found on PATH as `SEEK_CLAUDE_CLI_PATH`, `UnsetEnvironment=ANTHROPIC_API_KEY`), then daemon-reload, enable, restart; the CLI then waits for `/api/health`. Tested with an injected `systemctl` in `tests/test_service.py`. `README.md` documents install, data, every config key, agent registration, and troubleshooting; keep it current when config or setup changes.
- CLI sync: `sync_command.sync_channels(config, channel, transcripts, embedder, server_wait_seconds, poll_seconds, reindex, playlist)` probes `GET /api/syncs` on `HOST` (now in `config.py`) and hands off through `POST /api/syncs` (`syncs.enqueue_all`: every Active Library Channel, then every Active Playlist), `/api/channels/{id}/syncs`, or `/api/playlists/{id}/syncs`; with no server it runs a `SyncWorker` in-process via `run_until_finished(sync_ids)`, which respects the lease and returns once those Syncs finish. `--channel` matches a Channel's name (case-insensitive) or YouTube channel id (`find_channel`), and `--playlist` a Playlist's name or YouTube playlist id (`find_playlist`); `--all`, `--channel`, and `--playlist` are one mutually exclusive group on `sync`, `reindex`, and `backfill-storyboards`. Neither Channels nor Playlists can be added from the CLI. `backfill_command.backfill_storyboards(config, channel, transcripts, progress, playlist)` never goes through the server: it resolves its target to a `Scope` and fetches what `storyboards.missing(conn, scope)` lists. `cli.sync` waits 30 s for a server when `seek.service` is active. There is no systemd Sync timer: the server checks Channels and Playlists itself (`checks.run_checks`, started in the lifespan beside the worker, at start and every `create_app(check_seconds=)`, with `clock=` injectable). `syncs.enqueue_due(conn, now)` queues, through `_enqueue`, every Library Channel and every Playlist the pure `syncs.is_due` passes: Active, `check_every_hours` (6, 24, 168, or NULL for off; on `channels` since migration 17, on `playlists` from its creation) set, no queued or running Sync, and its latest Sync queued longer ago than the interval. One never synced isn't due, so the first Sync is always the user's. A Playlist's shape carries `next_check_at`, worked out by the server. It only queues, so the worker's throttle cooldown applies unchanged. Tests in `tests/test_sync_command.py` drive `sync_channels` against `harness.serving` (up) or a free port (down).
- Remote access: `proxy.ProxyMiddleware` (added last in `create_app`, so it runs first) refuses a `Host`, `X-Forwarded-Host`, or `Origin` outside `LOOPBACK_HOSTS` plus `config.allowed_hosts` (421/403), then takes scheme, host, and `X-Forwarded-Prefix` into the scope (prefix stripped by the proxy or not; Starlette wants `root_path` inside `path`). The `web_ui` route serves index.html with `<base href="{root_path}/">`. With `cf_access_team_domain` and `cf_access_aud` set, `access.AccessMiddleware` requires a valid `Cf-Access-Jwt-Assertion` except on direct requests (loopback peer, no `X-Forwarded-*`/`Forwarded`/`X-Real-IP`/`Cf-*` headers); keys come from `create_app(fetch_access_keys=, access_keys_refetch_seconds=)`, cached hourly and refetched for an unknown kid at most that often. Tests in `tests/test_remote_access.py` sign tokens with local RSA keys (`Certs`); `harness.event_stream` takes a path and headers.
- Models: `SentenceTransformerEmbedder` and `CrossEncoderReranker` (`models.py`) implement the `Model` port (`load()` never raises; `status()` is a `ModelStatus`) and raise `ModelUnavailable` until ready. Model statuses go out as `models` events and in Health. `uv run pytest -m real_models` runs the opt-in GPU test (models cached in `~/.cache/huggingface`; a llama-server usually holds 17 GB of the 3090).
- Passages: `segments.context` ("{title} — {chapter}", set at segmentation) frames each Segment for the embedder, the reranker, and FTS5 (`segments_fts(context, text)`, rebuilt by migration 7); `segments.passage_text` composes what is embedded. `search.spread_across_videos` caps results at `PER_VIDEO` (3) per Video and fills from the overflow. A reindex Sync (`syncs.reindex`, `POST /api/syncs`, `/api/channels/{id}/syncs`, or `/api/playlists/{id}/syncs` with `{"reindex": true}`, `seek reindex --all|--channel|--playlist`) steps done Videos back to `transcript_fetched` when claimed.
- Throttling: `VideoUnavailable(throttled=True)` is a refused caption fetch (the Video page itself still raises `SourceUnavailable` after yt-dlp's retries); `SyncWorker` fails the Sync after `THROTTLE_LIMIT` (3) in a row and skips claiming for `cooldown_seconds` (`youtube_backoff_seconds`, doubling per consecutive throttled Sync). `list_videos(channel_id, known_ids)` lists `/videos` then `/streams` (each tolerating a missing tab) and, given known ids, stops after a full page (`youtube.take_until_known`); the worker passes them once a Sync has completed unless most-recent or retry-failed. `youtube_cookies_from_browser` and `youtube_extractor_args` (a TOML table, or the table body in the env var) reach yt-dlp; fixed sleeps are jittered ±30%. "No captions" is transient within `CAPTIONS_GRACE` (7 days) of publish. `FakeChannel.streams` and `FakeTranscriptSource.listings_known` support the tests.
- Search: `search.Search.search(query, scope=, group=, channel_ids=, playlist=, limit=, prefer_recent=)` is the one entry point (`scope` is a `scope.Scope`, the Conversation's Group, Channel, or Playlist), served at `POST /api/search` (`search_api.py`) and by the MCP `search` tool. Every scope resolves to Videos, not Channels (ADR 0006): `scope.VIDEO_IN_SCOPE` is the one predicate for "searchable and covered" — done, not excluded, and either on an Active Channel in the Library or included in an Active Playlist; a Channel or Group scope requires the Active Library Channel, a Playlist scope only the Active Playlist. Search, `sources.py` (`expand`, `get_video`), saved Citations, the per-Channel counts in `groups.channel_summaries`, and frames (`storyboards.read_frames`, `missing`) all go through it; `scope.CHANNEL_IN_SCOPE` only names a scope's Channels (a Group's members, a Playlist's creators). Search resolves the scope to Video ids and filters KNN and FTS by `video_id` (`segment_vectors` is keyed by Video since migration 19). Each result carries `playlist_ids`, the Active Playlists that include its Video (`scope.ACTIVE_PLAYLIST_IDS`). Pure ranking steps (RRF, recency with `ranking.Recency`, matched cue) live in `ranking.py`. The Reranker port returns raw logits; recency is in the spec's "Implementation amendments".
- MCP: `mcp_server.create_mcp_server` builds an `MCPServer` (mcp 2.2; FastMCP is now `mcp.server.mcpserver.MCPServer`) with `list_groups`, `list_playlists` (`playlists.playlist_summaries`: Active Playlists with their creators), `list_channels` (Active Library Channels), `search`, `expand`, `get_video`, `sql`. The grounded-advisor text is `GROUNDED_ADVISOR`, in the instructions and every tool description. `create_app` serves it stateless with JSON responses at `/mcp`, runs the session manager in its own lifespan task (anyio cancel scopes can't cross tasks), and allows loopback plus `config.allowed_hosts` as Host/Origin (the app-wide guard below checks them first). Tools raise `ToolError` for user-facing errors via `_tool_errors`; anything else reaches the client as a message-less crash. `search` reuses `search_api`'s strict field types (`SearchQuery`, `GroupRef`, `ChannelIds`, `ResultLimit`) because the SDK validates tool arguments laxly. Expand and Video details live in `sources.py` (not-indexed Channels are NotFound); `GET /api/segments/{id}/expand` serves expand to the UI. `sql.run_query` is the read-only escape hatch (read-only URI, `query_only`, authorizer allowlist, progress-handler time limit, row/text/result-size and SQLite length limits).
- Web chat: `chat.Chat` runs one turn per Conversation as its own task (so it finishes and saves even if the browser leaves) and hands `chat_api` a queue, streamed as SSE with keepalives. Each turn builds `mcp_server.create_scope_server(database, search, scope)`: search fixed to the Group, Channel, or Playlist, expand/get_video NotFound outside it, no sql, and the instructions and tool names its kind has in `mcp_server._BOUND` (`list_groups` only for a Group; a Playlist's `list_channels` lists its creators). `ChatRequest` carries that server, `bound_tool_names(scope)`, and its system prompt. A Conversation may fix a canonical local project directory and/or web access when it starts; the composer’s **Add context** popover sets these. `claude_chat.chat_options` then adds only read-only `Read`/`Glob`/`Grep` tools inside that project (a `PreToolUse` hook rejects path and symlink escapes) and/or `WebFetch`/`WebSearch`, while user settings, other MCP servers, shell, and edits stay off. Resource-enabled prompts keep Channel-derived claims grounded and cited but distinguish direct project/web observations. `conversations.py` stores Conversations (`scope_kind`; `group_id`/`channel_id`/`playlist_id`, each SET NULL on delete; `scope_name` kept current by renames; `create_conversation` refuses a Paused Channel or Playlist, a Group with no Channels, or a Playlist with no Videos with 409, and a Channel outside the Library with 404) and messages; the question is saved before the turn, the answer on `ChatDone` with its tool calls, the session id, and Citations resolved from the answer's YouTube links (`chat.citation_links`) against the scope's searchable Videos. `chat_events` maps SDK messages and strips the `mcp__seek__` prefix; streams are closed with `contextlib.aclosing` so the CLI process stops. The web UI reads the POST stream through `api.sendMessage`.
- Conversations: `GET /api/conversations` (`?group_id=`, `?channel_id=`, or `?playlist_id=`; more than one is 422) lists them most recently active first (by newest message id; timestamps are only to the second) with a title from the first question, and `GET /api/conversations/{id}` returns the messages; every shape carries `scope: {kind, id, name}`. The read-only rule: a Conversation's scope id is read from the column its `scope_kind` names, and a NULL there means 409 on send ("was deleted, so this Conversation is read-only") while it stays readable. A deleted Group, Channel, or Playlist nulls it through the foreign key; `channels.leave_library` nulls `channel_id` itself, so a Channel's old Conversations stay read-only even after the creator is added again under the same id. Playlist Conversations start at `POST /api/playlists/{id}/conversations`. `ChatRequest.history` holds the earlier messages, replayed by the adapter when there is no session to resume; `ChatFailed.session_lost` makes `Chat` retry once without the session, which only the Claude CLI path can need. `ChatEngine.status()` backs the Health `chat` field, which reports both engines and the active one (ticket 06); the Claude CLI's probe is `claude auth status --json`, cached, and the API engine's is a read of the stored credential with no provider call. In the UI, App holds the open chat (`opening` remounts it; a finished turn only updates the chat it came from) and a `Conversations` section refreshed by a version counter.
- Live updates: `events.Events` is an in-process broker served as SSE at `GET /api/events` (`events_api.py`). Publish `sync`/`video` records after the write that changed them, or `syncs`/`videos` when a list needs reloading. A `video` or `videos` event is named by where its Videos are listed, not by the Sync that changed them (`videos.Listed`): `channel_id`, the Channel they are credited to, and `playlist_ids`, every Playlist that includes the Video (for `videos`, any of that Channel's Videos). So a Playlist's reload is one `videos` event per creator (`videos.listed_by_creator`), and a Channel page follows a Playlist Sync and the reverse. Deleting a Channel or a Playlist publishes `syncs`, then a `videos` event per Channel whose Videos remain. The UI subscribes through `useLiveList` (or `useServerEvents` for non-lists) in `web/src/events.ts`; nothing polls.
- YouTube adapter: parsing and error classification are pure functions in `youtube.py` (tested in `tests/test_youtube.py`); the `YouTubeTranscriptSource` class only runs yt-dlp sessions, pacing and retrying Sync calls. `uv run pytest -m real_youtube` runs the opt-in live test.
- Store: `db.Database.run(fn)` runs blocking work on a thread with a fresh connection. Writes go through `db.transaction(conn)` (`BEGIN IMMEDIATE`, guarded rollback). Do read-backs inside the transaction. Migrations are appended to `db.MIGRATIONS`: a string entry is additive only, a callable entry is a rebuild run with foreign keys off and checked before commit (migration 9, `_channels_not_mentors`); never edit a shipped entry. Exception: the vec0 table `segment_vectors` and its delete trigger are created after migrations by `db.ensure_embedding_model` (dimension comes from the model), so a migration can't reference them on a fresh database; one that changes the table's shape rebuilds it only where it exists and never renames it into place (migration 19, `_vectors_by_video`).
- Sync pipeline: `videos.pipeline_stage` is the last completed stage; failure (`failure_stage` = stage attempted) and exclusion are separate columns, and the API derives a single `stage`. `SyncWorker._advance` runs each Video through its remaining stages; `videos.complete_stage` advances and clears failures. Segments are replaced per Video in one transaction; FTS5 and vec0 rows follow via triggers. Pipeline store functions return False/None when their row vanished mid-Sync (Channel or Playlist deleted) rather than raising; the stage writes after the fetch (`segments.record_segments`, `record_embeddings`, `videos.record_done`) return a `StageOutcome`, "gone" for that and "stopped" for a Video excluded since the Sync took it up (`videos.standing`; deleting a Playlist or a Channel re-judges inline, mid-Sync), which the Sync then leaves alone and goes on. A Sync's source is a `videos.Source` (`kind` channel or playlist, `id`): the `syncs` row has exactly one of `channel_id` and `playlist_id`, the `Sync` shape carries both plus `source_name`, and queueing, claiming, counts, retry-failed, and reindex all take a `Source`. Exclusions (minimum length plus Channel filters, bundled as `videos.ExclusionRules`) are recomputed for the whole Channel at discovery by `videos._apply_exclusions`; an excluded Video loses its Segments and steps back to `transcript_fetched` (`videos._set_exclusion` is the one place an exclusion is set or lifted). Inclusion wins: a Video any Playlist includes, Active or not, is judged by the minimum length only and takes no place in a Channel's most-recent count. A Playlist Sync (`SyncWorker._discover_playlist`, `videos.record_playlist_discovery`) follows the listing: a creator not yet known becomes a Channel outside the Library (`channels.credited_channel`, its avatar looked up with `resolve_channel(paced=True)`), each Video is credited to its creator, memberships and positions are written to `playlist_videos`, and Videos the listing dropped leave the Playlist and go to the keep rule. A `PlaylistListing` carries `entries` (the videos with a creator) and `video_ids` (every video listed, in order): a video YouTube lists without its creator, as it does a private or deleted one, is never recorded, but a Video already in the Playlist stays while its id is listed, and `position` is the place among `video_ids`. A Channel's playlist filter also goes by `video_ids`. An empty listing for a Playlist that has Videos fails the Sync (`videos.EMPTY_LISTING`) and removes nothing. A Sync uses the filters as they were when claimed. `syncs.completed_videos` counts the Videos that reached done or failed during the Sync, so `web/src/lib/sync-status.ts` (`syncProgress`, `useNow`) can read a rate and a time remaining off the record and show the same estimate after a reload. Retry-failed is a Sync flag (`syncs.retry_failed`) that clears failures when claimed.
- Library: a Channel row is in the Library (`channels.in_library = 1`, migration 20) or outside it, where it exists only to credit a Playlist's Videos to their creator. Every Channel lookup requires `in_library = 1` (`channels._get_channel`, `list_channels`, `syncs._require_source`, `videos._require_channel`, `groups.set_members`, a new Conversation's scope, Search's chosen Channels), so one outside it answers 404 and is never synced on its own, grouped, or offered as a scope. `playlists.py` / `playlists_api.py` hold Playlists (`playlists`, and `playlist_videos` with `position`; migration 21): resolve, add, list, `PATCH` (name, `indexed`, `check_every_hours`; a rename updates `conversations.scope_name` and publishes `syncs`), delete. The keep rule is `videos.apply_keep_rule(conn, video_ids, min_duration_seconds)`, called inside the caller's transaction with Video ids read before whatever kept them is deleted: a Video some Playlist still includes is left alone; one whose Channel is in the Library is judged again from stored data (minimum length and the Channel's date window; the playlist filter and most-recent count catch up at the Channel's next Sync); any other is deleted, and then each creator outside the Library left with no Videos. Its three callers are `videos.record_playlist_discovery` (Videos a listing dropped), `playlists.delete_playlist`, and `videos.delete_channel`. `videos.delete_channel` (behind `DELETE /api/channels/{id}`; it lives in `videos` because `videos` imports `channels`) deletes a Channel none of whose Videos a Playlist includes, as before; otherwise `channels.leave_library` sets `in_library = 0`, clears the four filter columns and `check_every_hours`, removes its Group memberships and Syncs, and nulls its Conversations' `channel_id`, and the keep rule runs over its Videos. `channels.create_channel` brings a creator known outside the Library into it as the same row and id: Active, unfiltered, checked daily, no Sync queued; one already in the Library is still 409.

## Environment gotchas
