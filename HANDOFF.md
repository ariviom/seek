## Codebase conventions so far
- `create_app(config, transcripts, embedder, reranker, cli_engine, static_dir, sync_poll_seconds, events_keepalive_seconds, model_progress_seconds, sql_time_limit_seconds, fetch_access_keys, access_keys_refetch_seconds, secrets, api_engine)`: each port is its own argument, added when its first consumer lands; `secrets` and `api_engine` default to the production `KeyringSecrets` and an `ApiEngine` over it. Lifespan loads the models in the background and starts the `SyncWorker` task (`sync_worker.py`), which is woken on enqueue and on model state changes, and polls; it runs Syncs only while holding the `sync_lease` row, and only once the embedding model is ready (or has failed). `mentor serve` wires `YouTubeTranscriptSource` (yt-dlp, `youtube.py`, settings from `youtube_*` config), the real models from `models.py` sharing one `GpuRunner`, and `ClaudeChatEngine` with `claude_cli_path` or else the `claude` on PATH.
- Service: `mentor install-service` (`cli.install`) calls `service.install_service(config, env, mentor_executable, unit_dir, systemctl)`, which writes `mentor.service` (the shell's PATH, `MENTOR_*` and a few location variables, the Claude CLI found on PATH as `MENTOR_CLAUDE_CLI_PATH`, `UnsetEnvironment=ANTHROPIC_API_KEY`), then daemon-reload, enable, restart; the CLI then waits for `/api/health`. Tested with an injected `systemctl` in `tests/test_service.py`. `README.md` documents install, data, every config key, agent registration, and troubleshooting; keep it current when config or setup changes.
- CLI sync: `sync_command.sync_channels(config, channel, transcripts, embedder, server_wait_seconds, poll_seconds)` probes `GET /api/syncs` on `HOST` (now in `config.py`) and hands off through `POST /api/syncs` (enqueue all indexed Channels, `syncs.enqueue_all`) or `/api/channels/{id}/syncs`; with no server it runs a `SyncWorker` in-process via `run_until_finished(sync_ids)`, which respects the lease and returns once those Syncs finish. `--channel` matches a Channel's name (case-insensitive) or YouTube channel id. `cli.sync` waits 30 s for a server when `mentor.service` is active. `install_service(..., sync_schedule=)` also writes `mentor-sync.service` (oneshot `mentor sync --all`) and `mentor-sync.timer` (`Persistent=true`); a reinstall without a schedule refreshes the sync unit's environment and leaves the timer alone. The CLI validates the schedule with `systemd-analyze calendar`. Tests in `tests/test_sync_command.py` drive `sync_channels` against `harness.serving` (up) or a free port (down).
- Remote access: `proxy.ProxyMiddleware` (added last in `create_app`, so it runs first) refuses a `Host`, `X-Forwarded-Host`, or `Origin` outside `LOOPBACK_HOSTS` plus `config.allowed_hosts` (421/403), then takes scheme, host, and `X-Forwarded-Prefix` into the scope (prefix stripped by the proxy or not; Starlette wants `root_path` inside `path`). The `web_ui` route serves index.html with `<base href="{root_path}/">`. With `cf_access_team_domain` and `cf_access_aud` set, `access.AccessMiddleware` requires a valid `Cf-Access-Jwt-Assertion` except on direct requests (loopback peer, no `X-Forwarded-*`/`Forwarded`/`X-Real-IP`/`Cf-*` headers); keys come from `create_app(fetch_access_keys=, access_keys_refetch_seconds=)`, cached hourly and refetched for an unknown kid at most that often. Tests in `tests/test_remote_access.py` sign tokens with local RSA keys (`Certs`); `harness.event_stream` takes a path and headers.
- Models: `SentenceTransformerEmbedder` and `CrossEncoderReranker` (`models.py`) implement the `Model` port (`load()` never raises; `status()` is a `ModelStatus`) and raise `ModelUnavailable` until ready. Model statuses go out as `models` events and in Health. `uv run pytest -m real_models` runs the opt-in GPU test (models cached in `~/.cache/huggingface`; a llama-server usually holds 17 GB of the 3090).
- Passages: `segments.context` ("{title} — {chapter}", set at segmentation) frames each Segment for the embedder, the reranker, and FTS5 (`segments_fts(context, text)`, rebuilt by migration 7); `segments.passage_text` composes what is embedded. `search.spread_across_videos` caps results at `PER_VIDEO` (3) per Video and fills from the overflow. A reindex Sync (`syncs.reindex`, `POST /api/syncs` or `/api/channels/{id}/syncs` with `{"reindex": true}`, `mentor reindex --all|--channel`) steps done Videos back to `transcript_fetched` when claimed.
- Throttling: `VideoUnavailable(throttled=True)` is a refused caption fetch (the Video page itself still raises `SourceUnavailable` after yt-dlp's retries); `SyncWorker` fails the Sync after `THROTTLE_LIMIT` (3) in a row and skips claiming for `cooldown_seconds` (`youtube_backoff_seconds`, doubling per consecutive throttled Sync). `list_videos(channel_id, known_ids)` lists `/videos` then `/streams` (each tolerating a missing tab) and, given known ids, stops after a full page (`youtube.take_until_known`); the worker passes them once a Sync has completed unless most-recent or retry-failed. `youtube_cookies_from_browser` and `youtube_extractor_args` (a TOML table, or the table body in the env var) reach yt-dlp; fixed sleeps are jittered ±30%. "No captions" is transient within `CAPTIONS_GRACE` (7 days) of publish. `FakeChannel.streams` and `FakeTranscriptSource.listings_known` support the tests.
- Search: `search.Search.search(query, scope=, group=, channel_ids=, limit=, prefer_recent=)` is the one entry point (`scope` is a `scope.Scope`, the Conversation's Group or Channel), served at `POST /api/search` (`search_api.py`) and meant for ticket 11's MCP tool. Pure ranking steps (RRF, recency with `ranking.Recency`, matched cue) live in `ranking.py`. The Reranker port returns raw logits; recency is in the spec's "Implementation amendments".
- MCP: `mcp_server.create_mcp_server` builds an `MCPServer` (mcp 2.2; FastMCP is now `mcp.server.mcpserver.MCPServer`) with `list_groups`, `list_channels`, `search`, `expand`, `get_video`, `sql`. The grounded-advisor text is `GROUNDED_ADVISOR`, in the instructions and every tool description. `create_app` serves it stateless with JSON responses at `/mcp`, runs the session manager in its own lifespan task (anyio cancel scopes can't cross tasks), and allows loopback plus `config.allowed_hosts` as Host/Origin (the app-wide guard below checks them first). Tools raise `ToolError` for user-facing errors via `_tool_errors`; anything else reaches the client as a message-less crash. `search` reuses `search_api`'s strict field types (`SearchQuery`, `GroupRef`, `ChannelIds`, `ResultLimit`) because the SDK validates tool arguments laxly. Expand and Video details live in `sources.py` (not-indexed Channels are NotFound); `GET /api/segments/{id}/expand` serves expand to the UI. `sql.run_query` is the read-only escape hatch (read-only URI, `query_only`, authorizer allowlist, progress-handler time limit, row/text/result-size and SQLite length limits).
- Web chat: `chat.Chat` runs one turn per Conversation as its own task (so it finishes and saves even if the browser leaves) and hands `chat_api` a queue, streamed as SSE with keepalives. Each turn builds `mcp_server.create_scope_server(database, search, scope)`: search fixed to the Group or Channel, expand/get_video NotFound outside it, `list_groups` only for a Group, no sql. `ChatRequest` carries that server, `bound_tool_names(scope)`, and its system prompt. A Conversation may fix a canonical local project directory and/or web access when it starts; the composer’s **Add context** popover sets these. `claude_chat.chat_options` then adds only read-only `Read`/`Glob`/`Grep` tools inside that project (a `PreToolUse` hook rejects path and symlink escapes) and/or `WebFetch`/`WebSearch`, while user settings, other MCP servers, shell, and edits stay off. Resource-enabled prompts keep Channel-derived claims grounded and cited but distinguish direct project/web observations. `conversations.py` stores Conversations (`scope_kind`, `group_id`/`channel_id` SET NULL on delete, `scope_name` kept current; `create_conversation` refuses a not-indexed Channel or an empty Group with 409) and messages; the question is saved before the turn, the answer on `ChatDone` with its tool calls, the session id, and Citations resolved from the answer's YouTube links (`chat.citation_links`) against the scope's searchable Videos. `chat_events` maps SDK messages and strips the `mcp__mentor__` prefix; streams are closed with `contextlib.aclosing` so the CLI process stops. The web UI reads the POST stream through `api.sendMessage`.
- Conversations: `GET /api/conversations` (`?group_id=` or `?channel_id=`, both is 422) lists them most recently active first (by newest message id; timestamps are only to the second) with a title from the first question, and `GET /api/conversations/{id}` returns the messages; a deleted Group or Channel leaves them read-only (409 on send); every shape carries `scope: {kind, id, name}`. `ChatRequest.history` holds the earlier messages, replayed by the adapter when there is no session to resume; `ChatFailed.session_lost` makes `Chat` retry once without the session, which only the Claude CLI path can need. `ChatEngine.status()` backs the Health `chat` field, which reports both engines and the active one (ticket 06); the Claude CLI's probe is `claude auth status --json`, cached, and the API engine's is a read of the stored credential with no provider call. In the UI, App holds the open chat (`opening` remounts it; a finished turn only updates the chat it came from) and a `Conversations` section refreshed by a version counter.
- Live updates: `events.Events` is an in-process broker served as SSE at `GET /api/events` (`events_api.py`). Publish `sync`/`video` records after the write that changed them, or `syncs`/`videos` when a list needs reloading. The UI subscribes through `useLiveList` (or `useServerEvents` for non-lists) in `web/src/events.ts`; nothing polls.
- YouTube adapter: parsing and error classification are pure functions in `youtube.py` (tested in `tests/test_youtube.py`); the `YouTubeTranscriptSource` class only runs yt-dlp sessions, pacing and retrying Sync calls. `uv run pytest -m real_youtube` runs the opt-in live test.
- Store: `db.Database.run(fn)` runs blocking work on a thread with a fresh connection. Writes go through `db.transaction(conn)` (`BEGIN IMMEDIATE`, guarded rollback). Do read-backs inside the transaction. Migrations are appended to `db.MIGRATIONS`: a string entry is additive only, a callable entry is a rebuild run with foreign keys off and checked before commit (migration 9, `_channels_not_mentors`); never edit a shipped entry. Exception: the vec0 table `segment_vectors` and its delete trigger are created after migrations by `db.ensure_embedding_model` (dimension comes from the model), so a migration can't reference them on a fresh database.
- Sync pipeline: `videos.pipeline_stage` is the last completed stage; failure (`failure_stage` = stage attempted) and exclusion are separate columns, and the API derives a single `stage`. `SyncWorker._advance` runs each Video through its remaining stages; `videos.complete_stage` advances and clears failures. Segments are replaced per Video in one transaction; FTS5 and vec0 rows follow via triggers. Pipeline store functions return False/None when their row vanished mid-Sync (Channel deleted) rather than raising. Exclusions (minimum length plus Channel filters, bundled as `videos.ExclusionRules`) are recomputed for the whole Channel at discovery by `videos._apply_exclusions`; an excluded Video loses its Segments and steps back to `transcript_fetched`. A Sync uses the filters as they were when claimed. `syncs.completed_videos` counts the Videos that reached done or failed during the Sync, so `web/src/lib/sync-status.ts` (`syncProgress`, `useNow`) can read a rate and a time remaining off the record and show the same estimate after a reload. Retry-failed is a Sync flag (`syncs.retry_failed`) that clears failures when claimed.
- Errors: domain code raises `errors.NotFound` / `errors.Conflict`; ports raise `ChannelNotFound` / `PlaylistNotFound` (Sync-only, not in `ERROR_STATUS`) / `SourceUnavailable` / `ModelUnavailable` (its subclass `GpuOutOfMemory` fails only the Video being embedded, transcript kept, and the Sync goes on; Retry failed videos embeds it later), and `VideoUnavailable` for one Video (reason, permanent, language, partial details). All messages are user-facing and mapped to statuses in `app.ERROR_STATUS`.
- CLI status: `status_command.status(config, chat_engine)` and `list_all(config)` read `/api/health`, `/api/syncs`, and `/api/channels` plus `/api/groups` when the server answers, else the store (migrated first; no file is created). Tested against `harness.serving` and `harness.free_port`.
